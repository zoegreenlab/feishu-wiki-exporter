# 成功版本能力差异审计报告

## 一、确定事实

### 审计范围与方法

本报告仅比较以下本地文件和既有验收产物，未运行登录、导出、网络请求或任何写入型 Git 操作：

- 旧项目：`feishu-wiki-course-exporter-wiki-api/exporter.py`
- 旧项目备份：`feishu-wiki-course-exporter-wiki-api/exporter_success_backup.py`
- 公开项目：`feishu-wiki-course-exporter/exporter.py`
- 两项目的 `requirements.txt`
- acceptance-test 已生成的目录树、输出文件计数与失败日志。

### 目录与验收结果

- 旧项目与 acceptance-test 的 `full_wiki_tree.json` 均包含 68 个节点、54 个叶子节点。
- acceptance-test 的 `export_failures_browser.jsonl` 有 5 条记录，和“49 成功、5 失败”的验收结果一致。
- 这 5 条记录的错误类型均为 `RuntimeError`，错误文本均为 `feishu-docx` 返回退出码 `1`；记录的 stderr 为空。
- 旧项目当前输出目录中可观察到 56 个 Markdown 文件、324 个图片文件，且其 `export_failures_browser.jsonl` 为 0 行。该产物证明该次旧项目导出未记录页面失败，并包含图片资源。
- acceptance-test 输出目录中可观察到 51 个 Markdown 文件、160 个图片文件。Markdown 文件数不等同于成功页面数：当前产物无法单凭文件数判定每个页面的完整性或唯一性。
- 现有旧项目产物不能单独证实“曾成功导出 100+ 文档”这一历史数量；当前可核验的是上述 56 个 Markdown 文件和 0 条失败日志。该历史主张需要对应的当时输出清单或运行日志才能确认。

### 依赖与运行边界

- 两个项目的 `requirements.txt` 都只有 `playwright`，没有锁定 `feishu-docx` 的版本。
- `feishu-docx` 是终端中额外安装的外部 CLI，而不是项目 Python 依赖。
- 审计机器当前可调用的 `feishu-docx` 版本为 `0.2.7`；这不能证明旧成功运行或 acceptance-test 运行时使用的也是同一版本。

## 二、关键代码差异

### 当前旧项目与公开项目的 `exporter.py`

两者的稳定主流程相同：

```text
login → capture-network → build-tree → export-all-browser
```

两者的共同点：

- `login` 使用 Playwright 的有头 Chromium，保存 `data/storage_state.json`。
- `capture-network` 使用已保存的浏览器状态打开 Wiki 首页，只记录响应元数据。
- `build-tree` 从网络日志定位 `tree/get_info`，再用 Playwright request context 携带同一登录状态递归构建目录树。
- `export-all-browser` 只遍历没有子节点的页面，并以相同参数调用外部 CLI：

```text
feishu-docx export-browser <页面 URL> --storage-state <状态文件> --output <目录> --name <标题>
```

- 两者都在单页失败后继续处理其余页面，并记录失败日志。

唯一实质差异是公开项目将输出根目录参数化：

| 项目 | 输出根目录 |
| --- | --- |
| 旧项目当前 `exporter.py` | 固定的个人课程目录 |
| 公开项目 `exporter.py` | `--output-dir`，默认 `output/` |

该差异改变的是文件落点，不改变页面 URL、登录状态传递方式、`feishu-docx export-browser` 命令参数结构或失败处理方式。

### `exporter_success_backup.py` 的内容

该备份文件约 3,140 行，包含两类历史能力：

1. 大量探索/诊断命令：DOM 检查、网络捕获、目录接口检查、正文接口检查、资源字段检查等。
2. 一套已移除的自建导出路径：`export-page` 与 `export-all` 会自行读取浏览器状态中的 Cookie，调用 Wiki 的 `tree/get_node` 与 `docx/pages/client_vars` 接口，遍历 `block_map`，并自行生成基础 Markdown。

备份末尾还保留了 `export_all_browser`。该函数与旧项目当前稳定版的 `export_all_browser` 等价，仍然通过 `feishu-docx export-browser` 导出。

### 图片处理流程

| 能力 | 当前旧项目与公开项目稳定版 | `exporter_success_backup.py` 自建路径 |
| --- | --- | --- |
| 图片 URL 获取 | 不自行获取；交给 `feishu-docx` | 仅检查资源/图片字段用于诊断 |
| 图片下载 | 不自行下载；由 `feishu-docx` 负责 | 未发现下载实现 |
| Markdown 图片引用 | 不自行生成；由 `feishu-docx` 负责 | 未实现；图片会成为 `Unsupported block type: image` 注释 |
| 图片失败重试 | 无项目层重试；依赖 `feishu-docx` 自身行为 | 无图片下载或图片重试逻辑 |

因此，旧项目图片得以保留的可核验证据指向 `feishu-docx export-browser` 的外部处理能力，而不是备份中的自建 Markdown 逻辑。

### 登录状态与 Playwright 流程

当前旧项目和公开项目的登录与 Playwright 流程没有导出相关差异：

- 都用 `chromium.launch(headless=False)`；
- 都以 `context.storage_state()` 保存登录状态；
- 都通过 `new_context(storage_state=...)` 或 `request.new_context(storage_state=...)` 复用状态；
- 都将相同的状态文件路径传给 `feishu-docx --storage-state`。

## 三、导致成功率下降的可能原因（按概率排序）

### 1. 外部 `feishu-docx` 的页面级兼容性、运行版本或运行环境差异（高）

依据：5 个失败均发生在外部 CLI 返回退出码 `1` 时；公开版与旧稳定版的项目内导出调用几乎一致；项目没有锁定该 CLI 的版本。外部 CLI 对特定页面结构、资源类型、权限跳转、下载行为或运行环境的差异，是当前证据最能支持的方向。

限制：失败日志只保留 stderr，而本次 5 条 stderr 为空；无法据此定位到具体的不兼容内容或确认版本差异。

### 2. 验收运行时的会话状态或目标页面可访问性差异（中）

依据：`feishu-docx` 依赖传入的 Playwright storage state；即使目录接口可访问，个别页面、嵌入资源或跳转后的请求仍可能受到会话有效期、租户域、二次跳转或页面级权限影响。

限制：5 个失败页的 CLI 标准输出、浏览器控制台、HTTP 状态和复现记录均未保留，不能确认是权限问题。

### 3. 失败日志丢弃了 CLI 标准输出，导致根因被掩盖（中）

依据：项目将 `stdout` 定向到空设备，只保存 `stderr` 的末尾 1,000 字符；当前 5 条失败记录没有有效 stderr。若 CLI 将诊断写到 stdout，现有日志无法保留关键信息。

这解释“为什么无法判断”，但不是导致失败本身的直接原因。

### 4. 公开整理导致自建 API/Markdown 备用能力被移除（低至中）

依据：备份中确有自建 API 导出逻辑，公开项目没有保留。

反证：该自建路径不下载图片，也不生成图片 Markdown 引用；它不能解释旧项目的图片保留能力，更不能直接解释 `feishu-docx` 的 5 个退出码失败。它最多意味着公开版缺少一个可供诊断或降级的文本导出备用路径。

### 5. 输出目录参数化导致导出失败（低）

依据不足。代码差异仅影响输出根目录，且 acceptance-test 已成功生成 Markdown 和图片文件。除非存在特定文件系统权限、路径长度或冲突证据，否则不能将其列为主因。

### 6. 项目 Python 依赖变化（低）

两项目的 Python 依赖文件相同，均只声明 `playwright`。现有证据不支持 Python 项目依赖变更是主因；真正未锁定的是外部 `feishu-docx`。

## 四、恢复方案（不要执行）

### 方案 A：先补齐失败证据，再决定修复方向

做法：在隔离验收中保留每页 `feishu-docx` 的 stdout、stderr、退出码、实际命令版本和耗时；仅对 5 个失败页重跑。

优势：以最小范围区分页面兼容、会话、依赖版本与环境问题，避免把未验证的备份逻辑重新引入公开版。

风险：会产生新的测试产物，且需要有效登录状态；不应在未获授权的情况下执行。

适用场景：当前首选。现有失败日志不足以证明具体根因。

### 方案 B：固定已验证的 `feishu-docx` 版本并做小样本回归

做法：确认旧成功环境实际使用的 CLI 发布来源和版本，在隔离环境中固定该版本，对成功页、失败页和含图片页各选最小样本验证。

优势：直接处理当前最大的不可复现变量。

风险：历史版本未必可得；即使版本一致，账号状态和页面内容变化仍会造成差异。

适用场景：能取得旧环境安装记录、终端历史或可执行文件版本时。

### 方案 C：将备份的自建 API 导出作为受限诊断/降级工具

做法：仅在确定 `feishu-docx` 无法处理的页面上，验证备份路径能否导出文本；不把它视为图片保留方案。

优势：可以验证页面正文 API 是否仍可访问，帮助区分 CLI 问题和页面访问问题。

风险：自建路径依赖未公开接口、仅支持基础块类型且不支持图片下载；直接恢复到公开主链路会扩大维护与合规风险。

适用场景：只用于诊断或无图片要求的受限降级，不适合作为未经重建的替代主架构。

## 五、最小修改建议

以下为建议，不在本次审计中执行：

1. 不恢复 3,140 行备份代码，也不改变当前 `login → capture-network → build-tree → export-all-browser` 架构。
2. 在 `export-all-browser` 的单页子进程记录中保留 stdout、stderr、退出码和 `feishu-docx --version`，并继续使用现有的“失败后不中断”策略。
3. 增加一个仅面向验收的最小复现入口：可指定单个 Wiki URL 或 token，以便只复现失败页，而不是重跑全部 54 个叶子页。
4. 将外部 `feishu-docx` 的验证版本与安装来源写入验收记录；不要伪装为 `requirements.txt` 中已锁定的 Python 依赖。
5. 对“图片保留”设置独立验收条件：页面 Markdown 是否生成、图片文件是否落盘、Markdown 是否正确引用图片，三项分别记录。不要仅以 CLI 退出码或 Markdown 文件数量推断图片成功。

## 审计结论

现有证据不支持“GitHub 公开整理删除了当前主导出所需的图片能力”这一结论。公开版与旧稳定版当前的主导出实现一致，图片处理都委托给未锁定版本的外部 `feishu-docx`。最需要优先验证的是该外部 CLI 在验收环境对 5 个特定页面的实际诊断输出、版本和会话条件；在取得这些证据前，不应直接恢复旧备份或重构主架构。
